# Project Memory

## Project facts

- Project: AI Memory Gateway.
- Stack: Python 3.12, FastAPI, asyncpg/PostgreSQL, Jinja2 dashboard, OpenAI-compatible upstream APIs.
- Deployment: already modified by the user and successfully deployed on Zeabur.
- Main capability: gateway-owned closed loop of conversation capture, memory extraction, retrieval, consolidation, and prompt injection.

## Decisions

- Keep Python string delimiters and JSON examples in prompts as ASCII quotes. Commit `cb44263` changed `CONSOLIDATION_PROMPT` delimiters to smart quotes (`“””`) and its JSON example keys/values to curly quotes, causing a startup `SyntaxError` and invalid model JSON guidance; both were restored to ASCII.

- Treat this gateway and its PostgreSQL database as the sole source of truth for conversations and memories.
- Official Moonshot chat must use the full `https://api.moonshot.cn/v1/chat/completions` endpoint. When forwarding to the official Moonshot host with a `kimi-*` model, remove client-supplied `temperature` so fixed-temperature models such as Kimi K2.5 can select their legal server default; preserve temperature for `moonshot-v1-*` and non-Moonshot providers.
- Dashboard conversation deletion is permanent; there is no conversation recycle bin. Single and batch deletion transactionally remove conversation rows, the matching session cache, and matching token-usage rows, return the real number of deleted sessions, and preserve independently extracted long-term memories.
- Dashboard HTML and `static/js/dashboard.js` can be cached independently by the browser or deployment CDN. When new HTML buttons depend on new JavaScript functions, bump the dashboard script query version; entity deletion and split cognitive-draft buttons initially appeared inert because the template still referenced cached `dashboard.js?v=3.9`, fixed by advancing it to `v=4.0`.
- Add the Memory Constellations experience as a dashboard visualization module, not as a second memory gateway or parallel database.
- SiliconFlow can be used through its OpenAI-compatible APIs for both chat and embeddings; semantic retrieval should remain attached to the gateway's existing vector-search path.
- The constellation is a read-only `/constellation` page. It reuses the original project's canvas renderer and visual styling while consuming the gateway's `/api/memories`; visualization does not maintain a separate memory database.
- Dashboard pages other than the standalone constellation use one shared light dreamlike component system: ordinary controls, active navigation, active tabs, pagination, and cleanup actions use dark text over a near-white lavender/blush/peach glass gradient with pale blue restricted to the final 14%; primary controls use the same hues at slightly stronger saturation rather than an opaque dark block; destructive and success actions use light semantic rose and mint glass. Controls use low-contrast gray-purple/pink-purple edges and a diffuse downward shadow to create a floating Soft UI effect; avoid conspicuous white outlines and white inset rings across buttons, focus states, pagination, tabs, messages, modals, sliders, and mobile memory cards. Buttons must never fall back to the browser's gray default, and checked toggles/range thumbs reuse the primary glass token. Interactive hover uses only slight lift, gradient change, and diffuse glow; particle-gathering pseudo-elements are intentionally removed. The upper-right blue remains a small pale mist. Dashboard cache keys are `dashboard.css?v=5.9` and `dashboard.js?v=4.8`; `.main-content` must explicitly subtract the fixed sidebar width to avoid whole-page horizontal overflow on mobile. Memory titles are multiline editors and memory content defaults to six visible rows; at mobile width each memory row becomes a full-width vertical card with a 220px content editor.
- The standalone constellation keeps its read-only double-Canvas architecture but uses a softer deep-purple dreamlight palette, pastel nebulae, lavender bridges, matching glass controls without hover particle-gathering, and a horizontally scrollable mobile navigation. Its cache keys are `memory.css?v=4`, `main.js?v=5`, and `render.js?v=5`; background/nebula prerendering and the DPR cap remain unchanged for client-side performance.
- Entity MVP uses PostgreSQL `entities`, `entity_aliases`, and `memory_entities` as the canonical entity layer. New extracted memories carry explicit named entities into these tables; legacy memories are only backfilled through the bounded manual Dashboard action, with `memories.entity_scanned` preventing repeat charges for entity-free records. Retrieval prompt entries include linked entity names, and the star map now treats entities as constellations across People, Places, Projects, Events, and Life galaxies.
- Entity extraction admits only stable recurring long-term anchors. Both new-memory extraction and legacy backfill explicitly exclude implementation details and incidental technical terms; code also rejects confidence below 0.65 plus typical snake_case identifiers, function calls, filenames, and file paths before persistence. Existing noisy entities are left for manual review/deletion rather than automatically purged.
- Retrieval is entity-aware: `search_memories()` combines keyword candidates, optional vector candidates, and entity name/alias candidates. Entity hits recall linked active memories across layers 1/2/3, add `MEMORY_HW_ENTITY` to ranking, attach entity metadata to results, and inject one deduplicated matched-entity overview before the recalled memories.
- Entity retrieval uses a persistent cumulative-evidence lifecycle. `entities.evidence_count` initializes once from non-`inherited` links and increments only for a new extractor/backfill relationship; inherited event/core links remain normal entity memories but do not add evidence. Three cumulative observations, a confirmed profile, or a manual active override makes an entity retrievable; manual candidate overrides everything. Thirty-day archived-fragment cleanup deliberately preserves the cumulative count, while explicit memory deletion transactionally decrements still-traceable evidence. Candidate entities remain editable and keyword/vector-searchable but are excluded from entity recall, prompt entity metadata, and constellation grouping. Exact/full-phrase name matching rejects short and partial Latin names, entity recall is capped at three memories per matched entity, and retrieval logs omit queries, entity names, and memory content. Local verification passed 125 tests, Python compilation, JavaScript syntax, `git diff --check`, and Playwright at 760px with active/candidate groups, lifecycle controls, and no horizontal overflow; live PostgreSQL migration and deployed behavior remain unverified.
- Entity list rows use the shared dreamlike glass style as structured cards: identity/type, cumulative evidence, current memory count, aliases, and a detail affordance have separate visual hierarchy. Active entities use a responsive two-column grid where space permits, candidates remain collapsed by default, and mobile falls back to one column without horizontal overflow. Cache keys are `dashboard.css?v=6.0` and `dashboard.js?v=4.9`.
- Entity profiles are manual and evidence-backed: Dashboard draft generation reads up to 80 active linked memories, returns structured fields without writing, shows old/new profiles side by side, and only persists after confirmation. Saved profiles include evidence IDs, model, and update time; unsupported evidence IDs are rejected, and structured profile fields are included in entity-aware retrieval context.
- Confirmed entity-profile saves must be verified by reading the entity back from PostgreSQL. The API returns that persisted entity/profile, and the Dashboard reloads entity details from the authoritative row before showing success; a missing `profile_json` after update is an explicit server error rather than a false successful save. The corresponding dashboard script cache key is `v=4.1`.
- Entity-profile confirmation and detail reload must never fail silently: the Dashboard disables the save button while pending, handles network and non-JSON responses, preserves the draft on failure, displays the persisted profile immediately from the API response, and reports detail-reload errors separately instead of showing a false success. Metadata editing is explicitly labelled `保存名称/类型/别名` and does not imply profile generation. This advances the dashboard script cache key to `v=4.3`; live deployment behavior still requires the actual returned error or direct deployed-page access to verify.
- Entity records are manually editable in the Dashboard: display name, type, and the complete alias list are saved transactionally. Canonical names and aliases share a conflict-checked normalized namespace; renaming to an existing entity returns an explicit instruction to use entity merge. Entity-only deletion removes the entity row, inline profile, aliases, and memory links through existing cascades while preserving every original memory.
- The user is not an entity. `USER_ENTITY_NAMES` controls self-name exclusions; extraction, legacy backfill, and database linking reject those names, and startup removes existing matching entity rows without deleting memories. Entity summaries are compact AI-first-person current views: summary <=200 characters and supporting lists <=6 items. The Dashboard can open an existing profile without model generation and manually edit summary, relationship, stable facts, recent updates, preferences, uncertainties, and evidence memory IDs; generated drafts reuse the same full editor. Evidence IDs are shown beside linked memories and rejected client-side when they do not belong to the selected entity, while the existing backend validation and post-save PostgreSQL readback remain authoritative. The editor is desktop two-column and mobile one-column. Local verification covered JS syntax, 18 focused tests, Playwright manual-prefill, invalid-evidence rejection, successful mocked save/readback, and the 760px responsive breakpoint; deployed behavior remains unverified until release.
- Conversation-participant AI identities are also not ordinary entities. `AI_ENTITY_NAMES` defaults to `Huxley,栖,向野`; extraction and database linking reject these names, and startup removes matching entity rows plus cascading aliases/profiles/links while preserving the underlying memories. Participant knowledge belongs in the triadic cognitive model.
- Fragment, summary, entity-profile, and consolidated-event prompts identify the AI as `我是栖` and request 栖's first-person `我`; narrative voice is a generation-quality target, not a persistence gate, so third-person output remains stored for manual correction instead of being lost.
- The runtime system-prompt loader narrowly migrates only legacy leading identities `我是向野。` and `你是Huxley。` to `我是栖。`, including the database-backed prompt that takes precedence over `system_prompt.txt`; the remainder of customized prompt text is preserved.
- Fragment extraction resolves relative time from each persisted conversation message's `created_at` in `TIMEZONE_HOURS`, writes the absolute date directly into memory `content`, preserves the source expression's precision and plan/possibility status, and does not add structured temporal storage yet.
- Consolidated events include their absolute date naturally in `content` and return a per-event `event_date` saved through the existing database column; consolidation provides full local source timestamps and falls back to the selected range start only when the model date is invalid.
- Every fragment supplied to consolidation includes its own PostgreSQL `created_at`, converted through `TIMEZONE_HOURS` and labelled as `碎片生成时间：YYYY年M月D日 HH:MM`. Event content must contain `YYYY年M月D日`; when the model omits it or returns an invalid `event_date`, persistence falls back to the earliest generation date among that event's validated source fragments and prepends the Chinese absolute date.
- Consolidation responses are decoded with `llm_json.parse_json_array()` instead of a greedy first-`[`/last-`]` regex; bracketed model commentary, code fences, unescaped control characters, and trailing commas no longer invalidate an otherwise usable event array, and AI repair receives the complete response.
- Fragment archival follows successful event persistence: only validated in-range IDs from a created event are deactivated. Rerunning consolidation first reactivates date-range layer-1 fragments that are inactive but not referenced by any layer-2 event, repairing orphaned fragments from the former archive-all behavior.
- Zero-event consolidation is not caused by absolute-date fallback once fragments were fetched. Consolidation reads `reasoning_content` when `content` is empty, accepts in-range numeric string IDs, and reports returned/invalid-ID/empty-content event counts. Event selection favors fewer complete narratives; fragments need not all be covered, and singleton events require standalone long-term narrative value.
- LLM JSON extraction must not accept an illustrative `[]` in reasoning before the final answer. It selects the final non-empty top-level array while skipping nested `merged_ids`; a genuinely empty result triggers one explicit regeneration. Consolidation generation, JSON repair, and empty-result retry do not send `max_tokens`, and events have no word or sentence target. Narrative completeness and evidence-backed warmth are mandatory: participants, origin, interaction/progression, change, and outcome/current state must form a coherent lived first-person memory; length follows the evidence and event complexity.
- Fragment extraction also uses `llm_json.parse_json_array()`, sends no `max_tokens` cap, and retries once with an explicit JSON-only instruction when a response contains analysis but no array. A parse failure is an extraction failure, not evidence that the conversation contained nothing worth remembering.
- Entity-profile generation and legacy-entity backfill follow the same JSON-output discipline as fragment extraction: no `max_tokens` cap (a reasoning model's thinking previously consumed the 1800/2000-token budget, leaving `content` empty so the `reasoning_content` chain of thought was misparsed as the answer, failing with `Expecting value: line 1 column 1 (char 0)`), decoding through `llm_json` (`parse_json_object` for profiles, `parse_json_array` for backfill) instead of greedy first-`{`/`[` regex plus `json.loads`, and retrying once with an explicit JSON-only instruction when the response is empty or contains analysis but no JSON. Local verification passed 178 tests.
- The cognitive model is `三元一场` over the existing PostgreSQL `cognitive_items` table: one active `user_core`, `self_core`, `relationship_core`, and `current_field`. The first three are stable cores; `current_field` defaults to a 14-day review date and remains injected after that date only with an explicit possibly-stale warning. Existing six-slot data migrates deterministically and transactionally without an LLM call, keeping legacy rows as `superseded`; subsequent saves create a new active revision instead of silently overwriting the prior row. Dashboard draft generation reviews all four sections together through one review-only action, using a deduplicated maximum of 60 high-signal plus 20 recent active memories, and still requires per-section edit-and-save confirmation. Content keeps the approximately 240-character soft recommendation with no hard truncation or total cognition budget. Automatic persistence, background updates, and personality mutation remain deferred. Local verification passed 112 unit tests, Python compilation, JavaScript syntax, `git diff --check`, and Playwright checks at 1280px/760px with four cards, the dynamic-field editor, responsive two/one-column layout, and no horizontal overflow; live PostgreSQL migration and Zeabur behavior remain unverified.
- The constellation binary core represents the two participants rather than memory layers. Its default labels are `晏晏` and `栖`, configurable through `UI_USER_NAME` and `UI_AI_NAME`; event and core memories remain supporting content for those two stars.

- Partition-cache stability audit (local code-path evidence only, not a live Zeabur reproduction): a rotation request waits synchronously for `generate_summary()` for up to 60 seconds before `StreamingResponse` sends headers, creating a first-byte idle window that can look like an intermittent disconnect. The streaming proxy also emits no heartbeat while the upstream is silent, so `Connection: keep-alive` alone cannot prevent an intermediary idle timeout.
- Partition cache breakpoints are currently removed before forwarding: `build_partitioned_messages()` creates list-form content blocks with `cache_control`, but the unconditional `_sanitize_content_types()` call later converts every list-form content value to plain text. Enabling partition mode therefore changes history assembly and may add summary latency without preserving Claude cache breakpoints. This was confirmed from the local call order and transformation logic; upstream cache metrics and deployed behavior remain unverified.
- Long-thinking truncation is shared by cached and non-cached streaming paths. `stream_and_capture()` uses `httpx.AsyncClient(timeout=300)`, so the upstream read timeout is also 300 seconds between received bytes; it emits no downstream heartbeat while awaiting `aiter_bytes()`. `ReadTimeout` and other upstream stream exceptions are not caught inside the generator, so after the downstream 200/SSE headers have been sent the response ends abruptly without a structured error or `[DONE]`, and partial output is not persisted by the completion-only post-processing path.
- Runtime provider settings use non-empty Dashboard database values before Zeabur environment values and code defaults. When `DATABASE_URL` exists, startup loads Dashboard configuration even if the Zeabur `MEMORY_ENABLED` value is false, allowing the database value to take precedence. Dashboard saves and startup database restore synchronize `API_KEY`, `API_BASE_URL`, `MEMORY_API_KEY`, `MEMORY_API_BASE_URL`, and `MEMORY_MODEL` into the already-imported `memory_extractor` module, so extraction, entity profiles, and cognitive drafts use the displayed effective provider without waiting for another restart. Empty dedicated memory values still fall back to the effective main provider; invalid non-empty dedicated endpoints do not silently retry the main provider.
- The effective chat system prompt is resolved for each request through a cache with precedence `gateway_config.systemPrompt` (Dashboard) > `system_prompt.txt` > empty. Dashboard saves invalidate that cache, so the next normal or partition-cache request uses the saved prompt immediately; the file remains the fallback/default and is seeded into the database only when no non-empty Dashboard prompt exists.

- The shared streaming transport now uses a 30-second connect timeout with unlimited read time, emits an SSE comment heartbeat every 15 seconds without cancelling the pending upstream read, and converts HTTPX stream failures into an `upstream_stream_error` SSE payload followed by `[DONE]`. Upstream failures detected during iteration return through the normal completion path so already parsed content/reasoning is persisted; client cancellation still propagates and cancels the pending upstream read. Local verification: 41 unit tests, `py_compile`, `git diff --check`, and focused async heartbeat/protocol-error probes passed; live Zeabur idle-timeout behavior remains to be verified after deployment.
- Tool-chain intermediate responses are persisted but never trigger memory extraction while `assistant_tool_calls` remains non-empty. Chained tool calls therefore defer extraction until the first final assistant response without another tool request, which alone increments `MEMORY_EXTRACT_INTERVAL` and performs extraction. This removes the known duplicate extraction/load amplifier on the single-process Zeabur container; it does not by itself prove or eliminate every possible cause of a 20-second TCP connect timeout, and SSE heartbeat still only applies after a connection is established.
- Automatic extraction batching now uses PostgreSQL `memory_extraction_state`, keyed by `session_id`, with `last_extracted_message_id`, `pending_rounds`, and an expiring tokenized claim. A completed final response increments only its own conversation line; tool-call intermediates and re-rolls do not. Each claimed batch reads the exact user/assistant rows after the last successful cursor and through a fixed message-ID boundary, preserving timestamps without the former raw-row/final-message caps. Successful `[]` advances the cursor, while request or parse failure releases the claim without losing progress. First use after migration seeds each legacy line at its current message tail to avoid replaying all old history; delete, batch delete, merge, and rename synchronize the state. The gateway-owned active `session_id` is restored and reused in both partitioned and ordinary chat modes; the first real request creates it when absent, while auxiliary title requests do not. Local verification remains code-path and unit-test based until deployed PostgreSQL behavior is checked.
- Gateway client authentication accepts the gateway's `GATEWAY_SECRET` through standard `Authorization: Bearer`, while preserving `X-Gateway-Key` and `gateway_key`. Custom header and query values retain precedence when explicitly present. The incoming credential is only checked by the gateway middleware; upstream requests still construct a separate `Authorization` header from `API_KEY`. Local verification: 5 focused auth tests, all 50 unit tests with `PYTHONUTF8=1`, `py_compile`, and `git diff --check` passed; deployed Zeabur behavior remains unverified until release.
- The desktop memory table uses fixed layout without a minimum table width: layer is 64px, title 116px, and content flexes into the remaining width without the former 430px minimum. Compact auxiliary columns and cell padding keep Save/Delete visible while the content textarea wraps vertically; the action column remains sticky as a fallback. At `max-width: 768px` the existing vertical memory-card layout remains unchanged. Dashboard CSS cache key is `dashboard.css?v=5.9`. Local Playwright geometry at 1280px measured 938px container/table and 414px content; at 1024px it measured 722px container/table and 198px content, with no horizontal overflow at either width. Deployed browser behavior remains unverified until release.
- Fragment extraction requires one self-contained subject per memory and Qi's first-person voice. Event/interaction fragments require an evidence-backed feeling, while valuable objective information such as birthdays, occupations, account information, flight numbers, confirmed itineraries, or important contact details may remain factual without invented emotion. Account names, passwords, keys, flight numbers, and other character-sensitive values must be copied exactly, including case, digits, spaces, and special characters. Topics are not part of the extraction prompt or stored fields. High/medium/low are mapped to the existing 1-10 importance scale (8-10/4-7/1-3), so no Dashboard change is required.
- Fragment extraction product intent explicitly requires preserving important original quotes and retaining account passwords or keys when they have memory value; do not apply a generic credential-exclusion rule. `ENTITY_OUTPUT_GUIDANCE` is a separate entity-extraction concern appended to the same model request, not part of the fragment-content principles.
- Event consolidation groups fragments by one coherent event rather than by date, writes Qi's evidence-backed first-person emotion, preserves irreplaceable original quotes, omits irrelevant technical/process detail, and limits each complete event to 200 Chinese characters. Splits require disjoint evidence and independently complete sub-events; insufficient fragments remain active. The existing `event_date`, numeric `importance`, and `merged_ids` persistence contract remains unchanged, and fragment input now includes its numeric importance.
- Client dynamic environment snapshots use a transient user message marked with `metadata.dynamic_environment=true`. The gateway removes valid marked user/string snapshots before title detection, history reconstruction, persistence, summaries, and memory extraction, then injects only the last valid snapshot immediately before the latest real user message in the final Provider payload. An invalid marked message loses its internal metadata but remains an ordinary message so malformed or accidentally inherited metadata cannot delete a workflow request. Tool-loop requests reuse the identical client-supplied snapshot without server-side storage; Anthropic-style models merge the snapshot and real request at the send boundary with the snapshot first.
- Partition mode preserves every client-supplied system prompt for the current request. Gateway-owned system and memory rules remain first, followed by client system text in request order; client system prompts stay transient and do not enter PostgreSQL history, summaries, or memory extraction. Runtime logs report only the preserved prompt count and character total, never the prompt body.
- Partition request detection first aligns the longest unique PostgreSQL-history suffix with a continuous client-history segment using role, text, assistant tool-call IDs, and tool-result IDs. Only messages after that alignment are treated as the current Provider delta; strict tail detection remains the fallback for clients that send no overlapping history. The current user query is derived only from the validated current block and never falls back to an older client-history user. Ambiguous, empty, or structurally invalid partition deltas return `invalid_message_sequence` before memory retrieval, Drivesoid, upstream forwarding, persistence, or round accumulation. Logs contain role sequences, alignment coordinates, tool counts, and validation results but no message bodies.
- The gateway message path now classifies an immutable request copy before constructing a fresh Provider payload. Client system prompts remain transient but are preserved in both modes; dynamic environment, current time, cognition, recalled memories, and Drivesoid state never enter the persistence plan. Closed tool workflows are persisted through a per-session PostgreSQL advisory-lock transaction using longest suffix/prefix overlap, so retries only add missing messages and only a transaction that inserts a final assistant answer increments the extraction round.
- Partition context preparation reads system prompt, database history, cognition, recalled memories, and Drivesoid state concurrently. Summary-model rotation is scheduled after the response path begins and rechecks the partition state before committing; failures leave the current window unchanged for a later retry. Prompt bodies are not logged.
- Conversation chronology uses `conversations.id` as the authoritative order because messages inserted in one PostgreSQL transaction can share the same `created_at`. Final Provider payload validation permits multiple parallel `tool_calls` in one assistant message and tool results in any order, but rejects unclosed assistant calls, orphan/unknown/duplicate tool results, and missing/duplicate call IDs before contacting the upstream. Existing rows require no migration because their IDs already preserve insertion order. Local verification passed 130 tests, Python compilation, and `git diff --check`; Zeabur deployment remains unverified.
- Dashboard conversation details use `/api/conversation-messages?session_id=...` so session IDs containing `/` are not interpreted as URL path segments; the legacy path endpoint remains available. The frontend now surfaces non-2xx or non-JSON responses instead of displaying them as `0 / 0`, detail rows use ID order, and the Dashboard script cache key is `v=5.0`. Local verification passed 131 tests, Python/JavaScript syntax checks, and `git diff --check`; deployed behavior remains unverified.
- Dynamic environment snapshots accept string content, while text-only content-block lists must also retain the `<dynamic_context ...>...</dynamic_context>` envelope. This prevents inherited `dynamic_environment=true` metadata from deleting a real list-form workflow request before partition alignment; invalid markers lose internal metadata and remain ordinary messages. Conversation persistence independently normalizes every content value to PostgreSQL-safe text, so list-form messages and upstream rejection paths cannot roll back the batch with `expected str, got list`. Content without usable text becomes `[图片]`. Local verification remains local-only until deployed workflow behavior is checked.
- Abandoned tool chains self-heal request-side instead of permanently locking a session. When the current block is recognized, `repair_stale_tool_chains()` neutralizes zero-result zones in the assembled history before forwarding: assistant `tool_calls` with no matching result are stripped (content-less assistants dropped) and ownerless tool results dropped. Fully closed chains — including cross-boundary closures where the database assistant pairs with the current delta's results — and partial closures (parallel set only partially returned), mismatched, duplicate, or missing-ID chains are never touched; those keep the existing strict `invalid_message_sequence` rejection, as do unrecognizable current blocks. The gate covers both ordinary-user blocks and tool-result requests: a tool-result request whose database history contains older dangling chains (accumulated by previously rejected requests) still has those stale chains neutralized while the chain it is actively closing passes through untouched, so a session polluted by past failures recovers on the next tool use. The repair is a pure request-side pass: no DB writes, no background tasks, so a later tool-result request still closes the chain naturally through the normal persistence path. Deferred v2 work: request-gated DB writeback folded into the `persist_conversation_batch` advisory-lock transaction with an `abandoned` metadata flag excluded from provider rebuild and memory extraction, and a full-tail scan instead of a 200-row window. Local verification passed 23 focused repair tests and the full 167-test suite under UTF-8; deployed behavior remains unverified.
- Partition alignment supplies the calling assistant from the database when a client returns tool results without the matching `assistant(tool_calls)` message in its resent history (common with plugin-style clients and format bridges). If the database tail's assistant call IDs exactly equal the client's trailing tool-result IDs, the chain closes across the request boundary (`db_assistant_supplied`, including parallel results in any order and clients that send only the tool messages) instead of failing with `no_valid_current_block`. ID mismatches, database tails that are not the caller, and every previously valid shape keep their existing behavior. The unrecognizable-block 400 response now includes the reconciliation `reason` field for fast diagnosis. Local verification passed 165 tests under UTF-8; deployed behavior remains unverified.
