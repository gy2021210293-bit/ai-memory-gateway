# Project Memory

## Project facts

- Project: AI Memory Gateway.
- Stack: Python 3.12, FastAPI, asyncpg/PostgreSQL, Jinja2 dashboard, OpenAI-compatible upstream APIs.
- Deployment: already modified by the user and successfully deployed on Zeabur.
- Main capability: gateway-owned closed loop of conversation capture, memory extraction, retrieval, consolidation, and prompt injection.

## Decisions

- Keep Python string delimiters and JSON examples in prompts as ASCII quotes. Commit `cb44263` changed `CONSOLIDATION_PROMPT` delimiters to smart quotes (`“””`) and its JSON example keys/values to curly quotes, causing a startup `SyntaxError` and invalid model JSON guidance; both were restored to ASCII.

- Treat this gateway and its PostgreSQL database as the sole source of truth for conversations and memories.
- Official Moonshot chat must use the full `https://api.moonshot.cn/v1/chat/completions` endpoint. When forwarding to the official Moonshot host with a `kimi-*` model, remove client-supplied `temperature` so fixed-temperature models such as Kimi K2.5 can select their legal server default; preserve temperature for `moonshot-v1-*` and non-Moonshot providers.
- Dashboard conversation deletion is permanent; there is no conversation recycle bin. Single and batch deletion transactionally remove conversation rows, the matching session cache, and matching token-usage rows, return the real number of deleted sessions, and preserve independently extracted long-term memories.
- Dashboard HTML and `static/js/dashboard.js` can be cached independently by the browser or deployment CDN. When new HTML buttons depend on new JavaScript functions, bump the dashboard script query version; entity deletion and split cognitive-draft buttons initially appeared inert because the template still referenced cached `dashboard.js?v=3.9`, fixed by advancing it to `v=4.0`.
- Add the Memory Constellations experience as a dashboard visualization module, not as a second memory gateway or parallel database.
- SiliconFlow can be used through its OpenAI-compatible APIs for both chat and embeddings; semantic retrieval should remain attached to the gateway's existing vector-search path.
- The constellation is a read-only `/constellation` page. It reuses the original project's canvas renderer and visual styling while consuming the gateway's `/api/memories`; visualization does not maintain a separate memory database.
- Dashboard pages other than the standalone constellation use one shared light dreamlike component system: ordinary controls, active navigation, active tabs, pagination, and cleanup actions use dark text over a near-white lavender/blush/peach glass gradient with pale blue restricted to the final 14%; primary controls use the same hues at slightly stronger saturation rather than an opaque dark block; destructive and success actions use light semantic rose and mint glass. Buttons must never fall back to the browser's gray default, and checked toggles/range thumbs reuse the primary glass token. Interactive hover uses only slight lift, gradient change, and diffuse glow; particle-gathering pseudo-elements are intentionally removed. The upper-right blue remains a small pale mist. Dashboard cache keys are `dashboard.css?v=5.3` and `dashboard.js?v=4.5`; `.main-content` must explicitly subtract the fixed sidebar width to avoid whole-page horizontal overflow on mobile. Memory titles are multiline editors and memory content defaults to six visible rows; at mobile width each memory row becomes a full-width vertical card with a 220px content editor.
- The standalone constellation keeps its read-only double-Canvas architecture but uses a softer deep-purple dreamlight palette, pastel nebulae, lavender bridges, matching glass controls without hover particle-gathering, and a horizontally scrollable mobile navigation. Its cache keys are `memory.css?v=4`, `main.js?v=4`, and `render.js?v=4`; background/nebula prerendering and the DPR cap remain unchanged for client-side performance.
- Entity MVP uses PostgreSQL `entities`, `entity_aliases`, and `memory_entities` as the canonical entity layer. New extracted memories carry explicit named entities into these tables; legacy memories are only backfilled through the bounded manual Dashboard action, with `memories.entity_scanned` preventing repeat charges for entity-free records. Retrieval prompt entries include linked entity names, and the star map now treats entities as constellations across People, Places, Projects, Events, and Life galaxies.
- Entity extraction admits only stable recurring long-term anchors. Both new-memory extraction and legacy backfill explicitly exclude implementation details and incidental technical terms; code also rejects confidence below 0.65 plus typical snake_case identifiers, function calls, filenames, and file paths before persistence. Existing noisy entities are left for manual review/deletion rather than automatically purged.
- Retrieval is entity-aware: `search_memories()` combines keyword candidates, optional vector candidates, and entity name/alias candidates. Entity hits recall linked active memories across layers 1/2/3, add `MEMORY_HW_ENTITY` to ranking, attach entity metadata to results, and inject one deduplicated matched-entity overview before the recalled memories.
- Entity profiles are manual and evidence-backed: Dashboard draft generation reads up to 80 active linked memories, returns structured fields without writing, shows old/new profiles side by side, and only persists after confirmation. Saved profiles include evidence IDs, model, and update time; unsupported evidence IDs are rejected, and structured profile fields are included in entity-aware retrieval context.
- Confirmed entity-profile saves must be verified by reading the entity back from PostgreSQL. The API returns that persisted entity/profile, and the Dashboard reloads entity details from the authoritative row before showing success; a missing `profile_json` after update is an explicit server error rather than a false successful save. The corresponding dashboard script cache key is `v=4.1`.
- Entity-profile confirmation and detail reload must never fail silently: the Dashboard disables the save button while pending, handles network and non-JSON responses, preserves the draft on failure, displays the persisted profile immediately from the API response, and reports detail-reload errors separately instead of showing a false success. Metadata editing is explicitly labelled `保存名称/类型/别名` and does not imply profile generation. This advances the dashboard script cache key to `v=4.3`; live deployment behavior still requires the actual returned error or direct deployed-page access to verify.
- Entity records are manually editable in the Dashboard: display name, type, and the complete alias list are saved transactionally. Canonical names and aliases share a conflict-checked normalized namespace; renaming to an existing entity returns an explicit instruction to use entity merge. Entity-only deletion removes the entity row, inline profile, aliases, and memory links through existing cascades while preserving every original memory.
- The user is not an entity. `USER_ENTITY_NAMES` controls self-name exclusions; extraction, legacy backfill, and database linking reject those names, and startup removes existing matching entity rows without deleting memories. Entity summaries are compact AI-first-person current views: summary <=200 characters, supporting lists <=6 items, the Dashboard draft summary is editable before confirmation, and saving replaces the prior profile on the same entity.
- Conversation-participant AI identities are also not ordinary entities. `AI_ENTITY_NAMES` defaults to `Huxley,栖,向野`; extraction and database linking reject these names, and startup removes matching entity rows plus cascading aliases/profiles/links while preserving the underlying memories. Participant knowledge belongs in the triadic cognitive model.
- Fragment, summary, entity-profile, and consolidated-event prompts identify the AI as `我是栖` and request 栖's first-person `我`; narrative voice is a generation-quality target, not a persistence gate, so third-person output remains stored for manual correction instead of being lost.
- The runtime system-prompt loader narrowly migrates only legacy leading identities `我是向野。` and `你是Huxley。` to `我是栖。`, including the database-backed prompt that takes precedence over `system_prompt.txt`; the remainder of customized prompt text is preserved.
- Fragment extraction resolves relative time from each persisted conversation message's `created_at` in `TIMEZONE_HOURS`, writes the absolute date directly into memory `content`, preserves the source expression's precision and plan/possibility status, and does not add structured temporal storage yet.
- Consolidated events include their absolute date naturally in `content` and return a per-event `event_date` saved through the existing database column; consolidation provides full local source timestamps and falls back to the selected range start only when the model date is invalid.
- Every fragment supplied to consolidation includes its own PostgreSQL `created_at`, converted through `TIMEZONE_HOURS` and labelled as `碎片生成时间：YYYY年M月D日 HH:MM`. Event content must contain `YYYY年M月D日`; when the model omits it or returns an invalid `event_date`, persistence falls back to the earliest generation date among that event's validated source fragments and prepends the Chinese absolute date.
- Consolidation responses are decoded with `llm_json.parse_json_array()` instead of a greedy first-`[`/last-`]` regex; bracketed model commentary, code fences, unescaped control characters, and trailing commas no longer invalidate an otherwise usable event array, and AI repair receives the complete response.
- Fragment archival follows successful event persistence: only validated in-range IDs from a created event are deactivated. Rerunning consolidation first reactivates date-range layer-1 fragments that are inactive but not referenced by any layer-2 event, repairing orphaned fragments from the former archive-all behavior.
- Zero-event consolidation is not caused by absolute-date fallback once fragments were fetched. Consolidation reads `reasoning_content` when `content` is empty, accepts in-range numeric string IDs, and reports returned/invalid-ID/empty-content event counts. Event selection favors fewer complete narratives; fragments need not all be covered, and singleton events require standalone long-term narrative value.
- LLM JSON extraction must not accept an illustrative `[]` in reasoning before the final answer. It selects the final non-empty top-level array while skipping nested `merged_ids`; a genuinely empty result triggers one explicit regeneration. Consolidation generation, JSON repair, and empty-result retry do not send `max_tokens`, and events have no word or sentence target. Narrative completeness and evidence-backed warmth are mandatory: participants, origin, interaction/progression, change, and outcome/current state must form a coherent lived first-person memory; length follows the evidence and event complexity.
- Fragment extraction also uses `llm_json.parse_json_array()`, sends no `max_tokens` cap, and retries once with an explicit JSON-only instruction when a response contains analysis but no array. A parse failure is an extraction failure, not evidence that the conversation contained nothing worth remembering.
- The cognitive-model MVP uses one PostgreSQL `cognitive_items` table with six subject-bound slots: user identity/traits/preferences and current location/state/future plans; self identity/commitment and growth lesson; relationship practice/agreement and change. Saving a slot updates its active record and supersedes any older duplicate. Content has a 240-character recommendation but no hard truncation. All active confirmed slots are injected into both normal and partition-cached chat paths without a total cognition-character budget, in the fixed order user two slots, self two slots, then relationship two slots. The Dashboard has separate review-only draft actions for user, AI self, and relationship cognition. Each request restricts the model prompt and API validation to that subject's two slots, uses up to 80 high-signal active memories through the existing memory model/key/base URL, and still requires explicit edit-and-save confirmation. Automatic persistence, background updates, and personality mutation remain deferred.
- The constellation binary core represents the two participants rather than memory layers. Its default labels are `晏晏` and `栖`, configurable through `UI_USER_NAME` and `UI_AI_NAME`; event and core memories remain supporting content for those two stars.

- Partition-cache stability audit (local code-path evidence only, not a live Zeabur reproduction): a rotation request waits synchronously for `generate_summary()` for up to 60 seconds before `StreamingResponse` sends headers, creating a first-byte idle window that can look like an intermittent disconnect. The streaming proxy also emits no heartbeat while the upstream is silent, so `Connection: keep-alive` alone cannot prevent an intermediary idle timeout.
- Partition cache breakpoints are currently removed before forwarding: `build_partitioned_messages()` creates list-form content blocks with `cache_control`, but the unconditional `_sanitize_content_types()` call later converts every list-form content value to plain text. Enabling partition mode therefore changes history assembly and may add summary latency without preserving Claude cache breakpoints. This was confirmed from the local call order and transformation logic; upstream cache metrics and deployed behavior remain unverified.
- Long-thinking truncation is shared by cached and non-cached streaming paths. `stream_and_capture()` uses `httpx.AsyncClient(timeout=300)`, so the upstream read timeout is also 300 seconds between received bytes; it emits no downstream heartbeat while awaiting `aiter_bytes()`. `ReadTimeout` and other upstream stream exceptions are not caught inside the generator, so after the downstream 200/SSE headers have been sent the response ends abruptly without a structured error or `[DONE]`, and partial output is not persisted by the completion-only post-processing path.
- Runtime provider settings use non-empty Dashboard database values before Zeabur environment values and code defaults. When `DATABASE_URL` exists, startup loads Dashboard configuration even if the Zeabur `MEMORY_ENABLED` value is false, allowing the database value to take precedence. Dashboard saves and startup database restore synchronize `API_KEY`, `API_BASE_URL`, `MEMORY_API_KEY`, `MEMORY_API_BASE_URL`, and `MEMORY_MODEL` into the already-imported `memory_extractor` module, so extraction, entity profiles, and cognitive drafts use the displayed effective provider without waiting for another restart. Empty dedicated memory values still fall back to the effective main provider; invalid non-empty dedicated endpoints do not silently retry the main provider.
- The effective chat system prompt is resolved for each request through a cache with precedence `gateway_config.systemPrompt` (Dashboard) > `system_prompt.txt` > empty. Dashboard saves invalidate that cache, so the next normal or partition-cache request uses the saved prompt immediately; the file remains the fallback/default and is seeded into the database only when no non-empty Dashboard prompt exists.

- The shared streaming transport now uses a 30-second connect timeout with unlimited read time, emits an SSE comment heartbeat every 15 seconds without cancelling the pending upstream read, and converts HTTPX stream failures into an `upstream_stream_error` SSE payload followed by `[DONE]`. Upstream failures detected during iteration return through the normal completion path so already parsed content/reasoning is persisted; client cancellation still propagates and cancels the pending upstream read. Local verification: 41 unit tests, `py_compile`, `git diff --check`, and focused async heartbeat/protocol-error probes passed; live Zeabur idle-timeout behavior remains to be verified after deployment.
- Tool-chain intermediate responses are persisted but never trigger memory extraction while `assistant_tool_calls` remains non-empty. Chained tool calls therefore defer extraction until the first final assistant response without another tool request, which alone increments `MEMORY_EXTRACT_INTERVAL` and performs extraction. This removes the known duplicate extraction/load amplifier on the single-process Zeabur container; it does not by itself prove or eliminate every possible cause of a 20-second TCP connect timeout, and SSE heartbeat still only applies after a connection is established.
- Fragment extraction requires one self-contained subject per memory and Qi's first-person voice. Event/interaction fragments require an evidence-backed feeling, while valuable objective information such as birthdays, occupations, account information, flight numbers, confirmed itineraries, or important contact details may remain factual without invented emotion. Account names, passwords, keys, flight numbers, and other character-sensitive values must be copied exactly, including case, digits, spaces, and special characters. Topics are not part of the extraction prompt or stored fields. High/medium/low are mapped to the existing 1-10 importance scale (8-10/4-7/1-3), so no Dashboard change is required.
- Fragment extraction product intent explicitly requires preserving important original quotes and retaining account passwords or keys when they have memory value; do not apply a generic credential-exclusion rule. `ENTITY_OUTPUT_GUIDANCE` is a separate entity-extraction concern appended to the same model request, not part of the fragment-content principles.
- Event consolidation groups fragments by one coherent event rather than by date, writes Qi's evidence-backed first-person emotion, preserves irreplaceable original quotes, omits irrelevant technical/process detail, and limits each complete event to 200 Chinese characters. Splits require disjoint evidence and independently complete sub-events; insufficient fragments remain active. The existing `event_date`, numeric `importance`, and `merged_ids` persistence contract remains unchanged, and fragment input now includes its numeric importance.
